# 性能：做过什么、怎么找到的、为什么这么改

输入法的性能预算只有一条：**每一键的候选必须在 10 ms 内算完**（用户敲键间隔 100 ms 上下，超过 30 ms 就能感觉到黏），
启动尽量 1 s 内。联想走后台线程不算在内。这篇按时间顺序记每一轮优化：起因、怎么定位、改了什么、数字前后对比，
以及走过的弯路。数字都是 release 构建、开发测试词库（89 万条）、300 万对 bigram 的 M 系列 Mac 上量的。

## 怎么量

- `cargo run --release -p cloudime-cli -- <拼音>` 打每个阶段的耗时：parse（切分 + 纠错）、lookup（词库查询）、
  rank（排序 + 各类插入，整句转换算在这里）、translate（释义查表）。
- `--typing` 逐键模式（2026-09-05 加）：把 `kaifa` 当 k、ka、kai、kaif、kaifa 五次按键，每个前缀查一次，
  一行一键。这才是输入法的真实工作量，一次性查整段会漏掉「首键最贵」「简拼越敲越贵」这类问题。
- 启动日志带各数据文件的加载耗时（`加载完成 dict_ms=…`、`语言模型已加载 load_ms=…`、`Engine 就绪 total_ms=…`）。
- 定位热点靠**临时打点**：在怀疑的函数里 `Instant::now()` 累加、`eprintln!` 打出来，看完删掉。机器上没有装 profiler，
  而且 IME 进程也不方便挂 profiler；打点够用，前提是先打点再改（见下面的弯路）。
- 测试性能改动不改行为：词库查询有一份线性扫描版只在测试里用，随机词库 + 随机模式与收窄版对拍，结果集必须相同；
  排序 / 整句的改动靠现有单元测试和 CLI 上一组固定输入回归。

## 第一轮：内存（2026-09-03）

**起因**：词库从几十条样例换成 89 万条真实数据，进程 RSS 480 MB。每条词一个 `String` + 一个 `Vec<String>` 音节，
分配器开销和指针比数据本身还大。

**改法**：arena + 偏移。所有词文本首尾相接放一个 `String`（`texts`），所有拼音键放另一个（`keys`，同音词共用一个键），
索引是两个 `Vec` 的定长结构：`KeyIndex { key_start: u32, key_len: u16, first_slot: u32, slot_count: u32 }`、
`Slot { text_start: u32, text_len: u16, frequency: u32 }`。查出来的 `Match` 借用 arena 里的 `&str`，不拷贝。

**结果**：RSS 480 MB → 148 MB。这个布局也是后来二进制化（`.qj` 容器）能直接 mmap 的前提：内存里就是几段连续数组。

## 第二轮：查词（2026-09-04）

**起因**：单字母 `k` 一键 30 ms，全简拼 `zhgdoima` 70 ms，长全拼 20 ms。当时 `lookup_pattern` 是对整个索引线性扫、
逐键 split 音节比对。

**观察**：键按字节序排好，「以某段前缀开头的键」一定是连续区间。所以查词可以逐音节位置二分收窄：

- 完整音节：区间里直接二分到 `前缀 + 音节 + 空格`（`kai ` ），一步到位。
- 简拼位置（`k` 是前缀）：区间里出现的不同音节是一块一块的（`ka …`、`kai …`、`kan …`），每块只看第一条键就能算出这块的
  子区间，跳着扫，代价与实际出现的音节组合数成正比，与首音节下有多少键无关。
- 区间收到 48 条以内改成线性比对：小区间再二分加递归反而贵，全简拼时小块极多。
- `lookup_exact`（只要音节数正好等于模式长度的词）与 `lookup_pattern`（≥）同一套收窄，只是最后一级不收更长的词。
  整句转换的词图格子和「输入前缀也出候选」都只要精确等长的词，之前用 ≥ 版再过滤，白查一大片长词。

**同一次查询里的重复**：不同切分共享很多前缀（`zh g d o…` 的几种切法前几段一样），同一个前缀模式只查一遍（`HashMap` 记忆化，
键是模式串）。

**排序**：单字母简拼命中两万条，`sort_by` 的比较器里每次 `chars().count()` 让排序占几十毫秒。改成排序键先算好再排
（`SortKey` 元组，文本借自词库），远超上限时先按结构键 + 词频 `select_nth_unstable` 砍到 2 × 上限再算上下文得分、再排，
候选最多 500 条（同音字最多的音节也不到这个数，再往后没人翻）。去重只做到够数为止。

**结果**：长输入 20 ms → 0.2 ms，`zhgdoima` 70 ms → 1–3 ms，单字母 30 ms → 3–4 ms。

## 第三轮：逐键（2026-09-05）

**起因**：简拼整句、拼写纠错、英文模式几个功能叠上去之后，想在给测试者打包前系统量一遍。先加了 `--typing` 逐键模式，
一跑就看到三个极端：`zhzhzhzhzhzhzhzh` 16 键 44 ms（parse 39 ms），`sssssssssssssss` 15 键 21 ms（rank 13 ms），
单字母首键 9–10 ms。常规输入（`woxiangquchifan`、`kaifa`）都在 1–4 ms，问题全在简拼极端情况和首键。

### parse 39 ms：纠错变体

拼写纠错对「不像话」的拼音枚举一处编辑的全部变体（换位、替换、插入、删除，16 字母约 1500 个），每个变体跑一次
完整切分 DP（`parser::segment`，带 `Vec<Segmentation>` 克隆和排序）。任何非末尾有简拼的输入都算「不像话」，
所以全简拼句子每键都在做这件事，而且长度越长变体越多、每个变体的 DP 也越贵，二次增长。

**改法**：加一个只回答是否、不分配的 `parser::is_fully_segmentable`（一维可达性 DP，每个位置查 trie 拿合法音节长度），
变体先过它，剩下的几个才做真正的切分。**结果** 39 ms → 0.17 ms。

### rank 13 ms：整句词图的格子查词（弯路在这里）

`sss…` 15 个音节，词图有 15 × 8 = 92 个格子（最长词 8 音节），每个格子对词库做一次 `lookup_exact`。

先后猜错了两次：

1. 猜是格子内的排序：比较器里每次查两张哈希表（用户选择次数、个人出现次数）。改成得分先算好再排——没变化（12.6 → 11.9 ms）。
2. 猜是路径打分里的 bigram 查找：300 万对 `(u64 键, 计数)` 扁平数组二分，一次 22 步随机访问。改成按前词分组的 CSR
   （`offsets[v]..offsets[v+1]` 是 v 的后继段，段内按后词编号二分），内存 48 MB → 24 MB——也没变化（11.6 ms）。

然后才打点：92 个格子查词共 25 000 条原始命中、10 ms；路径打分只有 0.7 ms。**热点是词库收窄本身**：
`s s s s` 这种简拼格子要把词库里所有 s 开头音节的组合走一遍，每步一两次二分，这是第二轮那个算法的固有代价，
再怎么调常数也省不掉。

**改法**：不省这一次，省后面十四次。敲键是增量的——第 n+1 键只新增以它结尾的最多 8 个格子，其余格子上一键都算过。
加 `sentence::SpanCache`：键是格子模式（每个位置的写法与是否完整，含模糊音写法），值是排好、截好的候选（`Arc<[SpanWord]>`，
不再借用词库）。候选只与词库、用户词、选择次数、个人出现次数有关，Engine 在 commit / `learner_mut` / 换 Learner 时整个清掉；
超过 8192 个格子也清。**结果** 12 ms → 1 ms，15 键平均 2.5 ms。

前两次改动保留了：得分预算是对的写法，CSR 是更好的布局（也是二进制化时的布局），只是它们不是这个瓶颈。
教训写在最后。

### 首键 9 ms：单字母命中 78 000 条

`s` 一键：`lookup_pattern([s…])` 把所有首音节 s 开头的词全收进来（78 573 条），然后每条算一次用户权重（哈希查表）、
一次模糊音比对、构造 `Scored`，再进预选。打点分摊：查词 1.9 ms、构造 3.0 ms、预选 + 排序 3.8 ms、插入 1.4 ms
（这 1.4 ms 是 `jiff` 首次加载时区，进程生命周期里只有一次）。

改了四处，每处都是常数级：

- 词频、语言模型词表、个人 n-gram 的 `HashMap` 换 `foldhash`（SipHash 一次几十纳秒，这里一键要查几万次）。
- 预选键从 9 元组打包成一个 `u128`（精确、覆盖字母数、简拼数、末音节完整、选择次数、词频、模糊、字数依次占位），
  `select_nth` 比整数而不是逐项比元组；预选边界上的平手不再拿文本决胜，谁留下无所谓，最终排序仍用完整键。
- 没开模糊音时不逐条做模糊命中比对（`is_fuzzy_hit` 要 split 音节）。
- `scored.reserve(hits.len())`，省掉几次翻倍搬家。

**结果** 首键 9–10 ms → 4.5–5.6 ms，模糊音全开 8 ms。

| `sss…` 15 字母 | 21 ms | 4.5 ms |
| 单字母首键 | 9 ms | 5 ms（模糊音全开 8 ms） |

启动里词库解析 0.24 s、语言模型表 0.62 s，这是 TSV 逐行 parse + 建哈希表的成本，靠算法省不掉，要改文件格式（下一节）。

## 第四轮：启动（2026-09-05，`.qj` 容器）

**起因**：启动 0.93 s，词库 TSV 解析 0.24 s、语言模型两张 TSV 解析 + 建哈希表 0.62 s。这是 89 万行 + 350 万行的逐行 parse、
排序、`HashMap` 插入，算法上没得省，要改文件格式。

**改法**：`crates/cloudime-format` 的 `.qj` 容器（设计见 [design/architecture.md](../design/architecture.md)）。要点是**内存布局就是文件布局**：
第一轮的 arena + 偏移、第三轮的 CSR 本来就是几段连续数组，直接落盘；打开时 mmap，只校验头、分节边界、每条偏移是否越界。
语言模型的 `HashMap<String, (id, count)>` 换成文件里的开放寻址哈希索引（槽里放编号、键留在 arena、FNV-1a + fmix64 稳定哈希），
TSV 解析路径也改成产出同样的结构，查询代码只有一份。

**弯路**：第一版 `Text::deref` 用带校验的 `from_utf8`，每次取 `&str` 都扫一遍 30 MB arena，CLI 直接卡死超时。
打开时校验一次、之后 unchecked 才是对的；unsafe 的前提（文件只整体替换、从不就地修改）写在注释里。

**结果**：

| | 改前 | 改后 |
|---|---|---|
| 词库加载 | 240 ms | 12 ms（其中大半是逐条校验偏移） |
| 语言模型加载 | 620 ms | 9 ms |
| Engine 就绪 | 930 ms | 50 ms |
| 文件体积 | dict.tsv 26 MB + lm TSV 48 MB | dict.qj 46 MB + lm.qj 46 MB |

体积反而大了：TSV 里词频是十进制文本，容器里是定长 `u32`，加上哈希表一半是空槽。以后要减体积就上变长编码，
但那会破坏零拷贝，除非只对冷字段（词频）做。首键从冷页开始时多 2–3 ms（缺页），`madvise(WILLNEED)` 已开，
再要就启动时后台线程摸一遍页。

## 第五轮：释义表进容器（2026-09-05）

> 说明：候选词释义表这一功能已在 0.0.1 开发期整体移除，本节是当时的优化记录。

**起因**：释义表全量生成后从 6 万词涨到 24 万词，TSV 解析从 20 ms 涨到 90 ms，启动 170 ms。

**改法**：`Glossary` 改成双存法：TSV 解析出来还是哈希表；`.qj` 是字符串 arena + 词条表（词的偏移、释义段）+ 释义表
（译文 / 读音 / 词性缩写各一段偏移）+ 文件里的哈希索引，与词库、语言模型同一套 `cloudime-format`。查表时按需拼出 `Translation`，
每键几百次、每次几十纳秒的哈希加几次切片。**结果** 释义表加载 90 ms → 8 ms，启动 170 ms → 47 ms（冷启动 116 ms，缺页）。

## 第六轮：词图敲错边（2026-09-06）

**起因**：整句词图每个完整音节多了十几种敲错写法（`correction::typo`），格子查词的分支随之变多。

**数字**（release，带用户数据，`--typing`）：28 键句子最慢 3.5 ms → 4.2 ms、平均 0.46 → 0.64 ms；40 键句子最慢 2.9 → 4.7 ms、平均 0.66 → 0.95 ms。
仍在每键 10 ms 的目标内。已做的收敛：换键只算相邻键（变体数少一半以上）；词级候选不加敲错边；整段一处编辑的变体上不再叠敲错边
（`nihoama` 的 parse 从 12 ms 回到 1 ms）；非末尾带简拼的切分、不到 4 个字母的不加。格子缓存的键含全部写法，敲错边不影响增量复用。
**没做的**：格子里敲错变体的命中先算全部再按 e^(−代价) 打折截断，理论上可以按代价分层、原样够多就不查变体，等数字需要再说。

## 第七轮：句末英文词（2026-09-08）

**改动**：`Engine::split_english_tail` 每次查询多做一遍「尾段是不是英文词」的扫描：从最长到最短试每个后缀查英文词表（哈希表），
命中且整段能读成拼音时再多跑两次整句转换比分（头段一次、整段末尾单字母也读一次），都走 `SpanCache`。
**数字**：`--typing woxiangxuehaorust` 每键最慢 5.0 ms（改前 4.65 ms），平均 0.8 ms；回放 4867 条与改前完全一致。
比分只在尾段真是词表里的词时才发生，平时的键只多几十次哈希查表。

**神经重打分**的延迟另记在 `neural-rescoring.md`：调研期在 M1 上量的 Metal 后端空前文单条 6 ms、64 字前文 × 8 条 133 ms，
离每键预算差一个量级，要做前文 KV 缓存与异步防抖（Windows 缺省 CPU，数字见下一轮）。

## 第八轮：本地整句模型（2026-09-08）

**起因**：字级 Transformer 重打分在整句评测集上过了门槛（+4.3 个点，见 `neural-rescoring.md`），但同步打分一次查询 60 到 70 ms、20 字长句 800 ms，
远超每键 10 ms 预算，不能放进按键回调。

**定位**：`cargo test --release -p cloudime-neural --features metal -- --ignored --nocapture` 的延迟探针（调研期在 M1 上量的，small 23M，8 条约 8 字的候选；现在 Windows 缺省 CPU，`metal` / `accelerate` 没人开）：

| 后端 | 空前文 1 条 | 空前文 8 条 | 64 字前文 1 条 | 64 字前文 8 条 |
|---|---|---|---|---|
| Metal，无缓存（改前） | 6 ms | — | — | 133 ms |
| Metal，前文 KV 缓存 | 6 ms | 20 ms | 8 ms | 28 ms |
| CPU（candle gemm），前文 KV 缓存 | 17 ms | 61 ms | 19 ms | 73 ms |

前文重算与缓存命中只差 1 到 2 ms：前文那 64 个 token 一次前向很便宜，贵的是每条候选一遍、每层十几个小算子的调度；
所以候选越多越慢，与候选长度关系不大，也是 CPU 反而更慢的原因（同样多次小算子）。

**改法**：
1. `cloudime-neural::PrefixCache`：前文（去掉最后一个 token）每层的 K / V 算一次存下来，候选只算「前文最后一个 token + 候选」；结果与 Python 打分对拍不变。
2. Core `engine/rescoring`：一次查询里整句转换跑好几遍（纠错变体、中英混输比分），所有路径文本进一张「前文 + 文本 → 神经分」缓存，
   同步打分器只补缺的分：评测每句 69 → 27 ms（`--eval-text` 300 句，λ 0.25 前文 64）。
3. 异步：打分在后台线程，按键回调只跑词级模型；壳停键 80 ms 后把缺分的文本一批送去，20 ms 轮询，到了重查一次只重画当前页。
   `--neural-async` 走同一条路，300 句上与同步逐句一致，每句 35 ms（含等待与两次查询）。

**结果**：按键路径回到改前（查询 0.7 ms），模型的意见在停键后约 100 到 130 ms 到（80 ms 防抖 + 一批 20 到 30 ms + 轮询间隔）。
模型后台加载 + 预热：进程冷启动 353 ms（fp16 56 MB mmap）；调研期那台 M1 首次编译 Metal 内核那次 12 秒，系统缓存后不再有（Windows 走 CPU 没有这一步）。
内存（调研期 M1 的 GPU 后端）：权重按 f32 上 GPU 时输入法进程 273 MB（其中 GPU 侧 172 MB）；改成 Metal 上缺省 f16 后 CLI 评测进程 240 → 131 MB（GPU 侧 185 → 60 MB），
300 句评测结果与 f32 逐句一致、与 Python 对拍仍在容差内，延迟略快（64 字前文 × 8 条 27 → 25 ms）。空闲时 CPU 0 到 1%，敲键那一刻 10 到 18%。
评测集全量（8322 句，`--eval-text`，同步模式，λ 0.5 前文 64）：改前平均 61 ms、最慢 781 ms；改后平均 24 ms、最慢 101 ms，命中率不变（41.6% / 79.1%）。

## GPU 可行性（2026-11-08，RTX 3060 8 GB / i5-12600KF）

**知意（int8 ONNX）——DirectML 能跑，而且整图都在 GPU 上**：用 `onnxruntime-directml` 1.24.4 加载同一个
`laya.int8g.onnx`，profiling 里整图融成一个 `DmlFusedNode`（`DmlExecutionProvider`，seq=64 时 kernel 2.2 ms）；
会话存活期间显存约 +170 MB（系统总占用 444 → 613 MiB）。不固定维度的 DML 比 CPU 慢；固定 `seq_len` /
`num_markers` / `num_slots` 后（`add_free_dimension_override_by_name`）才明显更快。下表是 `sess.run` 本身
（batch=1，不含分词与业务开销）：

| seq | CPU | DML 动态 | DML 固定 |
| --- | --- | --- | --- |
| 64 | 9.6 ms | 13.3 ms | 5.4 ms |
| 128 | 16.8 ms | 15.1 ms | 12.3 ms（p50 14.3） |
| 192 | 26.1 ms | 16.9 ms | 13.8 ms（p50 9.1） |
| 256 | 34.5 ms | 19.1 ms | 11.3 ms |
| 320 | 47.7 ms | 22.5 ms | 14.3 ms |

包体：DirectML 版 `onnxruntime.dll` 17.3 MB（CPU 版 14.2 MB），`DirectML.dll` 是系统自带（Win10 1903+；
1809 缺失就回退 CPU），运行时只多约 3 MB。代价是输入要 padding 到固定维度 / 分桶，短输入才有收益；
动态维度反而比 CPU 慢。

**固定维度 padding 的坑（2026-11-08）**：实测只把 `seq_len` 固定、`num_markers` / `num_slots` 保持动态，
已经能拿到几乎全部收益（seq=64：13.2 → 5.5 ms；再加 markers/slots 固定只差 0.1 ms）。但**不能直接补 0**：
模型里有 64 个 `DynamicQuantizeLinear`，量化 scale 是按整个激活张量（含 padding）算的；同一段真实输入
后面补 0 再跑，`attention_mask` 已经正确标 0、编码器 mask 也是 `-inf`，logits 仍会变约 0.1、
`char_logits` 变约 1.0 —— 动态量化 scale 被 padding 拉变了。rank 可能被改，不能当固定维度直接用。

**静态量化校准试过，不够用**：80 个校准样本、20 个验证样本，把 64 个 DQL 换成固定 scale
（全局 min/max、99.9% / 99% 截断都试了），验证集 logits 平均差 0.42–0.49、最大 0.91–1.05，
候选 top1 翻转 5–7 / 20。静态 per-tensor 比原来的 per-input 动态 scale 粗太多，不能接。

**现在的解法：padding 感知的动态量化**（`tools/zhiyi-padaware/`）：只改编码器里形状
`[1, seq, hidden]` 的 DQL，用 `attention_mask` 把 padding 换成 ±inf 后再 `ReduceMin/Max`，按有效 token
算 scale；scorer 里按 marker / slot gather 出来的 DQL 不动。CPU 上不 padding 时与原模型**逐位一致**，
padding 后有效位置也**逐位一致**（logits / char_logits 差都是 0）。

**但 DirectML 上这份图数值不稳**：同一份 padaware 模型，DML 与 CPU 的 logits 差约 0.07、`char_logits`
差约 0.5；padding 到 128 后差到 1.8 / 10。原模型在 DirectML 上也是 logits 差约 0.07、char 差约 0.5，
而且 Rust 的 DML 动态维度跑真实输入约 97 ms（CPU 4 线程约 17 ms）。所以：
- 固定桶 + padaware 在 DML 上**不能直接用**，没有启用；
- `OnnxForward` 加了启动探测：GPU 与 CPU 的 logits / `char_logits` 差超过 5e-3，或 GPU 比 CPU 慢 2 倍，
  就回退 CPU。当前 int8 模型在这台 RTX 3060 上会被探测拒绝；
- `[debugging] prefer_gpu_model` 仍然保留，换模型 / 换 GPU / 以后解决数值问题后可以重新启用。
DML 固定维度的速度参考（只说明性能，不代表能直接用）：64 / 128 / 256 / 320 约
6.6 / 8.5 / 13.3 / 16.6 ms，仍比 CPU 的 9.4 / 16.6 / 35.5 / 47.4 ms 快 2–3 倍。

**固定桶 + DML 的预期收益（2026-11-08）**：本机 `input-log.jsonl` 的 3.7 万条 commit 里，balanced
（前文按 64 字）估算 seq p50 ≈ 97、p90 ≈ 103，accurate（128 字）p50 ≈ 161；候选通常 9 条。真实 Rust
`ChoiceScorer::score`（16 字前文 / 9 候选）2 线程 13.3 ms、4 线程 10.4 ms、8 线程 10.4 ms；长前文
（116 字）2 线程 22.3 ms、4 线程 17.2 ms。DML 固定 128 约 8.5 ms、192 约 11 ms。相对当前 2 线程，
DML 典型省 5–9 ms、长前文省 10–13 ms；相对 4 线程只再省 2–7 ms。候选更新链路还有 80 ms 防抖 +
20 ms 轮询，总感知提升约 4–8%。**先把 `ZHIYI_THREADS` 从 2 提到 4（可配置）是零显存、零包体成本的
第一步**；全量多桶 DML 缓存每桶约 170 MB 显存、每个桶启动多约 1 秒，收益不足以默认开启，最多做单桶
opt-in 的 spike。

**含章（candle）——CUDA 能跑，但不适合随包**：candle 0.11 的 `cuda` feature 会把权重放显存，但
`candle-kernels` 的 build.rs 用 `cudaforge` 调 `nvcc` 编 PTX；本机只有驱动（CUDA 13.1），没装 CUDA Toolkit，
`nvcc` 不在 PATH，所以这次没编出 CUDA 版。运行期还要 CUDA runtime + cuBLAS（几百 MB），随安装包不现实；
candle 也没有 DirectML 后端。CPU 基线：加载 694 ms，8 条候选 77 ms（候选里有一条整句时长），权重 56 MB。

**含章 ONNX 导出 + 对拍（2026-11-08）**：`tools/model-export/` 把 `.qjm` 里的权重用 PyTorch 复刻后导出
完整序列 ONNX（f32 139 MB，fp16 70 MB），并按 candle 的 `score` 规则逐条对拍。四组用例（空前文、短前文、
8 候选、超过 128 token 的长前文）与 candle 的 `score` 总分最大差 **5.8e-4**（ONNX logits 最大差 6.5e-5），
排序不受影响。DirectML 上 8 候选从 candle CPU 的 77.1 ms 降到 12.9 ms，长前文 38.7 → 28.6 ms；
f32 模型显存约 +230 MB。fp16 更快更省，但 `score` 差会到 2.6e-2，适合“能用”而不是严格对拍。

带 `past_k` / `past_v` 的缓存模型也导了一版，与完整序列同样的对拍最大差 **5.9e-4**。CPU 上“前文一次 + 每批
候选一小步”在长前文是 13.8 + 7.9 ms（完整序列 60 ms），同一段前文反复打分只付 7.9 ms；短前文反而完整
序列更省。DirectML 上缓存模型的 step 因为 `past` 还是动态维度，反而要 26–33 ms，目前不如 DirectML 完整
序列（8 候选 13.2 ms / 长前文 27.8 ms）；要把 DML 缓存也压下来，下一步得把 `past` 也做固定桶。

**当前状态（2026-11-08）：GPU 接入先到这里，后续再优化。** 设置 → 调试的两个开关保留：
`prefer_gpu_model` 默认关，打开后先做启动探测，数值 / 速度不达标自动回退 CPU；`zhiyi_threads` 默认 4（1–32）。
DirectML 路径与 DML 版运行库已接入，但当前知意 int8 模型会被探测拒绝，实际仍走 CPU。后续可选方向：

1. **含章 float ONNX + DirectML**：实测准确、8 候选 12.9 ms（candle CPU 77 ms），下一步要接 Server 并解决
   模型体积 / 安装包（f32 139 MB，fp16 70 MB）。
2. **知意换 float / 静态量化模型**后重新验证 DirectML；当前 int8 DML 数值差约 logits 0.07 / char 0.5，
   动态维度约 97 ms（CPU 4 线程约 17 ms）。
3. **固定桶 + padaware** 在 DML 上不可用（padding 后 char 差约 10），除非先解决 DML 对动态量化的数值问题。

在数值问题解决前不要把 `prefer_gpu_model` 设为默认；`CLOUDIME_ZHIYI_DML_FORCE=1` 只用于开发验证。

强杀 AE 后候选窗没有跟着消失。

**短前缀查询限制（2026-11-08，随后改）：** 打点显示 `z` 这类单字母输入会从词库收到 17 万条命中
（`zh` 11 万），逐条建 `Scored` 再排序是 `lookup` / `rank` 的主要开销。处理：

- `cloudime-dictionary` 的查询收窄加了 `LookupLimit`：每键最多取 `per_key` 条、只收不超过若干音节的键
  （`lookup_pattern_alt_short` / `lookup_exact_alt_short`）；原有 `lookup_*` 走不限模式。
- Core 只对「**一个还没打完的音节**」（`z` / `zh`，`last.complete == false`）用 `max_syllables = 1`：
  单音节的字 / 词全留，多音节词等这个音节打完再出；`ni` / `kai` 这类完整音节和 `zhangwei` 不受影响。
- 一两个字母时每键最多取 64 条（`SHORT_PREFIX_PER_KEY`），更多只会在排序时被丢掉。

`--typing` 实测（release，完整 data/generated/dict.tsv）：

| 输入 | 改前 | 改后 |
|---|---|---|
| `z` | 33.8 ms（lookup 24.7 / rank 9.1） | 8.5 ms（lookup 7.8 / rank 0.7） |
| `zh` | 25.9 ms（lookup 18.6 / rank 6.7） | 7.6 ms（lookup 6.7 / rank 0.9） |
| `n` | 约 10 ms | 2.9 ms |
| `zhangwei` | 10.4 ms | 10.1 ms（完整音节，不受影响） |

AE 满载复测：`z` 的 Server `lookup` 从 20.4 ms 降到约 4–8 ms，按键处理回到 5–11 ms；
剩余候选窗延迟主要是 UI 首帧渲染（3–12 ms，受 CPU 抢占影响）。注意这是有意改变：
只打半个音节时不再出 `你好` / `你们` 这类多音节词；样例词库里的脚本重排用例因此从 `n` 改成 `kai`。

## 经验

1. **先量再改，先打点再改。** 第三轮猜错两次的原因是凭「常识」判断热点（哈希查表、大数组二分都是教科书里的慢点），
   而真正的热点是自己两天前写的、以为已经快了的收窄算法。两个改动花的时间比打点多得多。
2. **量真实的工作负载。** 输入法的真实负载是逐键增量查询，不是「查一次整段」。`--typing` 一加，之前一直测不出的问题
   立刻出来。同理，测极端输入（全简拼、重复字母、模糊音全开）而不只测顺手的例子。
3. **增量场景优先想缓存，而不是优化单次。** 格子查词的单次代价是算法固有的，但相邻两键 90% 的工作是重复的。
   缓存的难点是失效条件，要把「结果依赖什么」列清楚（这里是词库、用户词、选择次数、个人计数），在改这些东西的每个入口清缓存。
4. **常数优化要成批做并分别量。** 哈希器、键打包、跳过比对、预留容量，单看每项 0.5–1.5 ms，合起来首键砍掉一半。
   但它们排在算法和缓存之后，先做算法。
5. **数据布局服务两件事：查询速度和文件格式。** arena + 偏移、CSR 这些选择让内存结构可以直接落盘，二进制化（第四轮）只花了半天，
   而且解析路径和映射路径共用同一套查询代码。
6. **性能改动要有对拍或回归。** 收窄算法与线性扫描随机对拍；排序 / 缓存改动跑全部单元测试加固定输入组。
   没有这层保护，`select_nth` 换排序方向这种改动很容易悄悄改掉候选顺序。
